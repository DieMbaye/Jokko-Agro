# **Documentation Technique : Système de Certification Agricole Blockchain**

## **Introduction**

Notre plateforme de certification agricole numérique intègre une architecture blockchain complète pour garantir **l'immutabilité**, **la transparence** et **la traçabilité** des certifications produits. Cette documentation présente l'écosystème technique déployé, expliquant comment chaque composant contribue à créer un système de certification **fiable**, **vérifiable** et **indépendant**.

L'objectif principal est de transformer chaque étape de production agricole en **preuve numérique incontestable** :
1. **Documentation** via captures multimédias (photos, géolocalisation)
2. **Horodatage** certifié par le réseau Ethereum
3. **Stockage** décentralisé sur IPFS
4. **Vérification** publique par QR code

---

## **Écosystème Technique Global**

### **🌐 Infrastructure Décentralisée (Couche Stockage & Horodatage)**

**Combinaison : IPFS + Ethereum = Stockage Immutable + Horodatage Certifié**

**Pourquoi cette combinaison ?**
- **IPFS (InterPlanetary File System)** : Stockage décentralisé des preuves visuelles
- **Ethereum** : Horodatage incontestable via le consensus blockchain
- **Complémentarité** : IPFS stocke les données volumineuses, Ethereum les authentifie

**Implémentation dans notre projet :**
- **Photos des cultures** → Stockées sur IPFS via **Pinata** (service de persistance)
- **Hash des preuves** → Enregistrés sur **Ethereum Sepolia Testnet**
- **Liens permanents** :
  - `https://gateway.pinata.cloud/ipfs/{CID}` pour les photos
  - `https://sepolia.etherscan.io/tx/{transactionHash}` pour les vérifications

**Processus unifié :**
```
1. Photo → IPFS (Pinata) → CID unique
2. Hash(CID + métadonnées) → Ethereum (Smart Contract) → Transaction
3. Références stockées dans Firestore pour interface utilisateur
```

**Avantages :**
- **Coûts optimisés** : Stockage décentralisé économique
- **Persistance garantie** : Données accessibles même sans notre plateforme
- **Vérification indépendante** : Pas besoin de notre serveur pour prouver l'authenticité

### **🔗 Interface Utilisateur Blockchain (MetaMask + Remix)**

**Combinaison : MetaMask + Remix = Expérience développeur + utilisateur unifiée**

**Pourquoi cette combinaison ?**
- **MetaMask** : Interface utilisateur standard pour interagir avec Ethereum
- **Remix IDE** : Environnement de développement complet pour les smart contracts
- **Continuum** : Du développement (Remix) à l'utilisation (MetaMask)

**Implémentation dans notre projet :**

**Côté Développement (Remix) :**
- Développement du smart contract `CertificationRegistry.sol`
- Tests unitaires dans l'environnement JavaScript VM
- Déploiement sur Sepolia Testnet
- Génération automatique de l'ABI pour l'intégration Angular

**Côté Utilisateur (MetaMask) :**
- Connexion wallet pour l'identité numérique
- Signature des transactions de certification
- Gestion des frais de gas (gratuits sur Sepolia)
- Suivi des transactions confirmées

**Processus pour les producteurs :**
```typescript
// Dans notre service Angular
async registerProofOnBlockchain(proofData) {
  // 1. Vérifier la connexion MetaMask
  await this.ethereumService.connectWallet();

  // 2. Préparer les données pour le smart contract
  const contractData = this.encodeContractCall(proofData);

  // 3. Envoyer via MetaMask
  const result = await this.ethereumService.sendContractTransaction(
    CONTRACT_ADDRESS,
    contractData
  );

  return result.txHash; // Ex: 0x73bfae9eeafe6d87079757180baa89dc70e03eaa9a32e8d4d92d7bb70e964529
}
```

**Avantages :**
- **Expérience familière** : MetaMask utilisé par des millions d'utilisateurs
- **Sécurité maximale** : Clés privées jamais exposées à notre application
- **Portabilité** : Même identité sur différentes applications

### **📡 Infrastructure Backend (Alchemy + Firebase)**

**Pourquoi cette combinaison ?**
- **Alchemy** : Infrastructure blockchain professionnelle pour la fiabilité
- **Firebase/Firestore** : Base de données temps réel pour l'expérience utilisateur
- **Division des rôles** : Alchemy pour les données blockchain, Firebase pour l'interface

**Implémentation dans notre projet :**

  - Lecture des transactions (`eth_getTransactionReceipt`)
  - Suivi des blocs (`eth_blockNumber`)
  - Appels de contrats (`eth_call`)
- **Monitoring** : Analytics sur l'usage blockchain

**Firebase (Expérience Utilisateur) :**
- **Structure des certifications** :
  ```javascript

    productName: "Tomates bio",

      blockchainTransactionId: "0x...", // Lien Ethereum

      verified: true,
      timestamp: "2026-02-03T11:51:50Z"

  ```
- **Synchronisation temps réel** : Mise à jour automatique de l'interface

**Avantages :**
- **Performance** : Latence minimale pour les lectures blockchain
- **Scalabilité** : Gestion automatique de la charge
- **Développement rapide** : SDK Firebase pré-intégré avec Angular

### **🛠️ Stack de Développement (Angular + TypeScript + Services Spécialisés)**

**Combinaison : Framework Modulaire + Services Spécialisés**

**Pourquoi cette architecture ?**
- **Angular/TypeScript** : Structure robuste pour applications complexes
- **Services spécialisés** : Séparation claire des responsabilités
- **Maintenabilité** : Code organisé, testable, évolutif

**Architecture de nos services :**

```
src/app/
├── services/
│   ├── certification.service.ts          # Cœur métier certifications
│   ├── blockchain/                       # Module blockchain complet
│   │   ├── blockchain.service.ts         # Orchestrateur principal
│   │   ├── ethereum.service.ts           # Interactions Ethereum
│   │   ├── ipfs.service.ts               # Interactions IPFS/Pinata
│   │   └── blockchain-sync.service.ts    # Synchronisation automatique
│   └── auth.service.ts                   # Authentification
```

**Rôle de chaque service :**

**`blockchain.service.ts`** - Orchestrateur :
```typescript
class BlockchainService {
  // Flux complet : Photo → IPFS → Blockchain
  async createCertificationProof(photoFile, metadata) {
    // 1. Upload IPFS
    const ipfsResult = await this.ipfsService.uploadFile(photoFile);

    // 2. Calcul hash final
    const proofHash = this.calculateSHA256(ipfsResult.cid + metadata);

    // 3. Enregistrement blockchain
    const txResult = await this.ethereumService.registerProof(proofHash);

    return { ipfsCID: ipfsResult.cid, txHash: txResult.txHash };
  }
}
```

**`blockchain-sync.service.ts`** - Synchronisation :
- Vérification périodique des transactions
- Mise à jour automatique des statuts
- Gestion des erreurs et retry

**Avantages :**
- **Modularité** : Chaque service a une responsabilité unique
- **Testabilité** : Services isolés, tests unitaires simplifiés
- **Évolutivité** : Ajout de nouvelles blockchains facile

## **Types de Preuves Générées**

### **🖼️ Preuves Visuelles (IPFS)**
- **Photos originales** : Qualité complète, non compressées
- **Métadonnées** : JSON avec `{gps, timestamp, deviceInfo, productId}`
- **CID unique** : Identifiant immuable lié au contenu
- **Accessibilité** : Via gateway Pinata ou tout autre gateway IPFS

### **⛓️ Preuves Temporelles (Ethereum)**
- **Transaction hash** : Identifiant unique sur la blockchain
- **Block number** : Position dans la chaîne
- **Timestamp** : Horodatage certifié par le consensus
- **Signature** : Preuve d'identité du producteur

### **📊 Données Structurées (Firestore)**
- **Relations** : Liens entre checkpoints, photos, transactions
- **Statistiques** : Scores, progression, taux de réussite
- **Métadonnées utilisateur** : Préférences, historiques
- **Cache** : Données fréquemment accédées

## **Sécurité & Intégrité**

### **🔒 Architecture en Couches de Confiance**

**Couche 1 : Authenticité des Données**
- Hash SHA-256 des photos
- Signature numérique avec clé privée
- Vérification via contrat intelligent

**Couche 2 : Intégrité Temporelle**
- Horodatage blockchain (impossible à falsifier)
- Séquences de blocs (preuve d'ordre)
- Confirmations réseau (preuve de consensus)

**Couche 3 : Disponibilité**
- Réplication IPFS (multiple nodes)
- Persistance Pinata (pinning garanti)
- Sauvegarde Firestore (redundance cloud)

### **🛡️ Protection contre la Falsification**

**Scénario : Tentative de modifier un score dans Firestore**
```
Attaquant modifie : validationScore: 85 → 100
↓
Vérification détecte :
- Hash blockchain ne correspond plus
- Timestamps incohérents
- Signature invalide
↓
Résultat : ❌ "Falsification détectée"
```

**Implémentation :**
```typescript
async detectTampering(certificationId: string) {
  const firestoreData = await this.getFromFirestore(certificationId);
  const blockchainData = await this.verifyOnBlockchain(firestoreData.txHash);

  return {
    tampered: firestoreData.hash !== blockchainData.hash,
    details: {
      firestoreHash: firestoreData.hash,
      blockchainHash: blockchainData.hash,
      timestampDiff: Math.abs(
        firestoreData.timestamp - blockchainData.timestamp
      )
    }
  };
}
```
